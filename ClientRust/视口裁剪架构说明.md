# 视口裁剪架构说明：为什么不在 CameraSystem？

## 🤔 你的疑问

> calculate_visible_area 应该是视口裁剪，为什么不在 CameraSystem 里？

## 📍 当前实现位置

**视口裁剪逻辑位于**：`RenderSystem::draw_tiles()` 函数内部（第 380-500 行）

## 🎯 设计原因

### 1. 职责分离原则

```rust
CameraSystem {
    // 职责：相机本身的操作
    ✅ world_to_screen()   // 坐标转换
    ✅ screen_to_world()   // 坐标转换
    ✅ start_drag()        // 交互
    ✅ drag()              // 交互
    ✅ end_drag()          // 交互
}

RenderSystem {
    // 职责：渲染相关的优化
    ✅ calculate_visible_area()  // 渲染优化（视口裁剪）
    ✅ draw_tiles()              // 渲染执行
    ✅ apply_lod()               // 渲染优化（LOD）
    ✅ batch_render()            // 渲染优化（批处理）
}
```

### 2. 数据流向

```
Camera (数据) ──┐
Position (数据) ─┤
                ├──> RenderSystem.draw_tiles()
MapTiles (数据) ─┤        │
                 │        ├──> calculate_visible_area()
                 │        ├──> query tiles
                 │        └──> draw
VisibleArea (缓存)←────────┘
```

**视口裁剪的输入**：Camera + Position + MapTiles
**视口裁剪的输出**：VisibleArea（可见实体列表）
**视口裁剪的目的**：优化渲染，减少绘制数量

### 3. 性能考虑

视口裁剪是**渲染管线的一部分**，而不是相机功能：

```rust
// 渲染管线
fn draw_tiles() {
    // 步骤1：视口裁剪（基于相机计算可见区域）
    calculate_visible_area(camera, position);
    
    // 步骤2：LOD 过滤
    apply_lod_filter(zoom);
    
    // 步骤3：Z轴排序
    sort_by_z_order();
    
    // 步骤4：批量绘制
    batch_render(visible_tiles);
}
```

如果把视口裁剪放在 CameraSystem：
- ❌ 需要访问 MapTiles（CameraSystem 不应关心地图数据）
- ❌ 需要更新 VisibleArea（CameraSystem 不应关心渲染缓存）
- ❌ 耦合渲染逻辑（Camera 应该是通用的，不限于地图）

### 方案A：视口裁剪在 CameraSystem（你的想法）

**问题**：

- ❌ CameraSystem 需要知道 VisibleArea 的存在（耦合渲染缓存）
- ❌ 计算和渲染分离，可能数据不一致

### 方案B：视口裁剪在 RenderSystem（当前实现）✅

```rust
struct CameraSystem;

impl CameraSystem {
    // 纯粹的相机功能（通用）
    fn world_to_screen(...) { }
    fn screen_to_world(...) { }
    fn start_drag(...) { }
}

struct RenderSystem;

impl RenderSystem {
    fn draw_tiles(
        camera: &Camera,
        pos: &Position,
        world: &World,
        visible_area_entity: Entity,
    ) {
        // 步骤1：计算可见区域（基于相机参数）
        let visible_range = calculate_visible_range(camera, pos);
        
        // 步骤2：查询可见瓦片
        let visible_tiles = query_visible_tiles(world, visible_range);
        
        // 步骤3：更新缓存
        update_visible_area_cache(visible_area_entity, visible_tiles);
        
        // 步骤4：绘制
        draw_cached_tiles(visible_area_entity);
    }
}
```

**优点**：
- ✅ CameraSystem 保持纯粹（只管相机，不管渲染）
- ✅ 视口裁剪作为渲染优化的一部分（职责清晰）
- ✅ 计算和绘制在一起（数据一致性）
- ✅ 可以扩展其他渲染优化（LOD、批处理等）

```
        // 4. 绘制

    }
}
```

**相机只提供参数，渲染器负责优化和绘制。**

## 🔧 如果真的要放在 CameraSystem？

如果你坚持认为应该在 CameraSystem，可以这样重构：

### 重构方案：分离计算和应用

```rust
struct CameraSystem;

impl CameraSystem {
    // 纯计算：只计算可见范围，不访问世界数据
    fn calculate_visible_range(
        camera: &Camera,
        pos: &Position,
    ) -> VisibleRange {
        let projection_scale = 1.0 / camera.zoom;
        let half_width = camera.screen_width / 2.0 * projection_scale;
        let half_height = camera.screen_height / 2.0 * projection_scale;
        
        VisibleRange {
            left: pos.x - half_width,
            right: pos.x + half_width,
            top: pos.y - half_height,
            bottom: pos.y + half_height,
        }
    }
}

struct RenderSystem;

impl RenderSystem {
    fn draw_tiles(...) {
        // 1. 使用 CameraSystem 计算可见范围
        let range = CameraSystem::calculate_visible_range(camera, pos);
        
        // 2. 在 RenderSystem 中应用范围过滤
        let visible_tiles = self.query_visible_tiles(world, range);
        
        // 3. 绘制
        self.draw(visible_tiles);
    }
}
```

**这样的好处**：
- ✅ CameraSystem 提供可见范围计算（纯数学）
- ✅ RenderSystem 负责查询和绘制（渲染逻辑）
- ✅ 职责更清晰

## 🎯 总结

### 为什么当前设计是合理的？

1. **职责单一**：
   - CameraSystem = 相机操作（通用）
   - RenderSystem = 渲染优化（特定）

2. **数据局部性**：
   - 视口裁剪需要访问 MapTiles
   - MapTiles 只在渲染时需要
   - 放在 RenderSystem 避免不必要的耦合

3. **性能考虑**：
   - 视口裁剪、LOD、排序都是渲染管线的一部分
   - 统一在 RenderSystem 中，减少数据传递

4. **可扩展性**：
   - Camera 可以用于其他场景（UI、特效）
   - RenderSystem 可以添加更多优化（遮挡剔除、动态批处理）

---

### 建议

**保持当前实现**！✅

如果一定要优化，可以：
1. 提取 `calculate_visible_range()` 到 CameraSystem（纯计算）
2. 保留 `query_visible_tiles()` 在 RenderSystem（查询+绘制）

但这样增加的复杂度 > 收益。当前实现简单、清晰、高效。

## 🎓 ECS 设计哲学

**组件 = 数据，系统 = 逻辑**

```
Camera 组件：zoom, screen_size（相机参数）
         ↓
CameraSystem：相机操作（移动、缩放、坐标转换）
         ↓
RenderSystem：渲染管线（裁剪、LOD、绘制）
```

**关键原则**：
- 系统根据职责划分，不是根据数据划分
- 视口裁剪是渲染职责，不是相机职责
- 相机只提供参数，渲染器决定如何使用

**Remember**: 不要让 Camera 变成"上帝类"！🎯
