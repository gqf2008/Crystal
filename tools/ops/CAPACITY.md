# 容量标定草案（单机，2026-09-23）

> **口径先说清**：以下全部是**同一台机器**上跑「服务端 + 压测机器人」的结果
> （Windows 开发机，压测机与服务端机器合一）。它能回答「单机在什么会话数下开始劣化」，
> **不能**当作生产容量结论。生产容量需要独立压测机 + 生产拓扑（见文末"待外部资源"）。

## 1. 怎么测的

- 机器人：`tools/ops/bot.py`（协议级，不渲染）。世界会话 = 走完
  `ClientVersion → Login → StartGame(0)` 并保持连接（每 5s 一次 KeepAlive）。
- 账号：`tools/ops/seed_load_accounts.py` 离线播种——服务端对账号/角色创建有 IP 防刷
  （>2 账号/小时、>4 角色/小时 → 封 IP 24h），单机注册不出几百会话。
  **账号名必须是纯字母数字**：`validate_username` 拒绝下划线，实测 `ops_load1` 全部登录超时。
- 阶梯：`tools/ops/capacity_ramp.ps1`，每档**独立重启服务端**再压，避免上一步残留影响曲线。
- 观测：INFO 级心跳（`heartbeat: tick=… online=… monsters=… interval_ms=… lag_pct=…`）
  ＋ `gate mailbox full` / `kicking slow reader` 计数 ＋ 进程 RSS。

## 2. 登录路径（只握手 + 登录，不进图）

| 并发 | 成功 | p50 | p95 | 总耗时 |
|---|---|---|---|---|
| 30 | 30/30 | 0.21s | **0.27s** | 1.48s |
| 100 | 100/100 | 0.71s | **1.36s** | 1.50s |
| 200 | 200/200 | 1.55s | **2.96s** | 3.15s |

登录路径基本线性（门闸串行处理），200 并发仍零失败。

**注意这张表用的是早期指标 `login_sent`（包交给 OS 的时刻）**——它是"服务端读入是否被堵"的代理量，
不是登录延迟。修完 argon2 串行后同一指标塌到近 0，说明这个代理量对"服务端读入速度"很敏感、
对"客户端拿到回执"不敏感。**真延迟见 §2.1**。

（修复 gate 接入串行化之前，**30** 并发就要 7.78s——见 PR #3029。）

### 2.1 argon2 校验移出 AccountActor 之后（真登录延迟）

根因：`verify_password`（argon2id m=19456,t=2）跑在 AccountActor 的**串行邮箱里**，
是唯一把登录 p95 拉成斜率的 CPU 活。改法：把校验挪到 `spawn_blocking`（吃满 blocker 线程池），
结果用 `PasswordVerified` 回投，**状态改动与回包逻辑仍全在 actor 内**（封禁、错密码计数、
hash 迁移、在线判定语义不变）。

指标同时修正为 `login_reply_sec`（从发起连接到**收到登录回执**）：

| 并发 | 真延迟 p50 | 真延迟 p95 | 真延迟 max | 总耗时 |
|---|---|---|---|---|
| 100 | 0.192s | **0.351s** | 0.355s | 0.46s |
| 200 | 0.527s | **0.862s** | 0.886s | 0.99s |

对照口径说明：修前的 1.36s/2.96s 是旧指标（`login_sent`），**不能与真延迟直接相减**；
可比的证据是——同样的 bot、同样的机器，修前 200 个登录连接**连包都交不出去**（p95 2.96s），
修后 200 个登录 0.99s 内全部完成、真延迟 p95 0.86s。

## 3. 世界路径（进图并保持 20s）

### 3.1 扇出优化**前**（逐会话 `tell(SendToClient)`：一次广播 = N 条邮箱消息 + N 份 payload 拷贝）

| 并发 | 成功 | 登录 p95 | `gate mailbox full`（背压丢包） | 慢读者被踢 |
|---|---|---|---|---|
| 10 | **10/10** | 1.4–1.7s | 0 | 0 |
| 20 | 1/20 ～ 7/20 | 4.2–5.3s | 0 ～ 9741 | 0 |
| 30 | 0/30 | — | 17814 | 0 |
| 50 | 0/50 | — | 2711 | 0 |

**拐点在 10→20 会话之间**，且有两种劣化形态：

1. 20 会话：部分会话进图/保持失败，RSS 冲到 176MB，`gate mailbox full` 时有时无；
2. 30–50 会话：`gate mailbox full` 上万条——世界→客户端的 `SendToClient` 扇出把 gate 邮箱打满，
   数据被丢弃（这条丢弃逻辑本意是"一个人慢读别拖死全服"，代价是此时可见的丢包/卡顿）。

### 3.2 扇出优化**后**（`gate::actor::SendToClients`：一次广播 = 1 条消息 + 1 份 payload，`Arc` 共享）

| 并发 | 成功 | 登录 p95 | 丢包 | 慢读者被踢 |
|---|---|---|---|---|
| 10 | **10/10** | 0.004s | 0 | 0 |
| 20 | **20/20** | 0.20s | 0 | 0 |
| 30 | **24/30** | 5.73s | 0 | 0 |
| 50 | **28/50** | 5.75s | 10 | 0 |

**拐点从 20 抬到 30**：20 会话由 7/20 → **20/20**；30 会话由 0/30 → 24/30；50 会话由 0/50 → 28/50；
`gate mailbox full` 由 17814（30 会话）降到 **0**。语义未放宽——单会话通道满时仍按"慢读者"踢线。

**下一个瓶颈（已定位到现象，未修）**：30/50 会话时登录 p95 仍有 ~5.7s，但丢包/踢线为 0，
说明瓶颈已从"扇出背压"转到**登录/进场路径的串行化**：① 账号密码校验是 argon2id（m=19456,t=2，
CPU 密集）且在 AccountActor 串行处理——100/200 并发登录 p95 1.36s/2.96s 正是它的斜率；
② 每个 `StartGame` 要让 WorldActor 串行完成建号/发地图；③ `broadcast_to_map` 仍对每个目标
`ask(GetPlayerState)`（O(N) 邮箱往返），下一步应把 `map_index` 缓存进 `PlayerRecord` 去掉这轮 ask。

### 3.3 再测（扇出批量 + argon2 异步校验都在）

| 并发 | 成功 | 登录真延迟 p95 | `gate mailbox full` |
|---|---|---|---|
| 10 | 10/10 | 0.004s | 0 |
| 20 | **20/20** | 0.006s | 0 |
| 30 | 22/30 | 0.007s | 337 |
| 50 | **30/50** | 1.11s | 3443 |

① 的收益在**登录路径**上兑现得很干净（200 并发真延迟 p95 0.86s，见 §2.1）；
但**世界路径**的会话成功率仍是 ~30 会话一档，且丢包从 0 回到 337/3443——
说明剩下的瓶颈在**世界侧**：每次 `broadcast_to_map` 仍对每个目标 `ask(GetPlayerState)`
（O(N) 邮箱往返，20 人同图即 20 次 ask/广播），加上 `StartGame` 由 WorldActor 串行建号发图。
这两项是下一轮的明确目标（③ 缓存 `map_index` 进 `PlayerRecord`；② 拆 `StartGame`）。

### 3.4 ③ map_index 缓存（去掉每目标 ask）之后

改法：`PlayerRecord.map_index` 缓存 + **单一漏斗**维护——`PlayerActor::SetPlayerPosition` 每次应用
`map_index` 就 `tell(PlayerMapChanged)` 回投世界侧（换图的所有 27 处调用点最终都进这个 handler，
所以不可能"漏更新一处"）；读取方 `broadcast_to_map` / `same_map_players` 命中缓存即不问 actor，
未命中才回退 ask；debug 构建下仍与 actor 真值对拍（漏更新会在调试运行里炸出来）。

| 并发 | 成功（① 后 → ③ 后） | 丢包（① 后 → ③ 后） |
|---|---|---|
| 20 | 20/20 → **20/20** | 0 → 668 |
| 30 | 22/30 → **28~30/30** | 337 → 229 |
| 50 | 30/50 → **28~31/50** | 3443 → 301 |

**这是一次真实取舍，数据两条都摆出来**：③ 去掉了 O(N) 往返、会话成功率明显上升
（30 会话由 22/30 到 28~30/30），但第一轮测出**丢包也上升**（20 会话 0→992、30 会话 337→3910）
——因为原先每个目标的 ask 起了**意外的节流**作用，去掉后生产端比 gate 出队快，gate 邮箱满即丢。
（复用性：这正是"用错误的东西当节流器"的典型，删掉它必须同时补上正确的背压。）

**jev 判定（一次校验）**：`keep_and_fix_consumer` 0.980 / 置信 0.960（`keep_and_throttle` 0.010、
`revert_and_fix_consumer` 0.010）；并且「条目级丢包对玩家可见」p=0.740。
故：**保留 ③**，把消费端/tick 级合并作为下一步（而不是回滚）。

**下一步的真实约束（本轮新发现，必须记下来）**：消费端并非"随便加个节流就行"——
`GateActor` 处理 `StartGame` 时**故意**内联 `await world_ref.ask(...)`，因为 gate 邮箱的 FIFO 顺序
保证了"顶号解绑"发生在后续 `ClientDisconnected`/`LogOutCleanup` 之前（代码注释里写明这是替代
旧异步 tell 的确定性顺序，否则会把新会话的账号误置离线）。所以 ②（把 StartGame 的建号+发图
挪出 gate 串行路径）**不能简单 spawn 了事**，必须先定"解绑归谁做"（把 `session_usernames` 的
所有权/顺序契约重新设计），否则会复活一个已经修过的账号离线竞态缺陷。

### 3.5 消费端背压（世界侧有界发件箱）与"丢弃的真正来源"

补的背压：`broadcast_to_map` 遇到 `gate mailbox full` 时**不再丢**，改为进世界侧有界发件箱
（上限 8192 条），每 tick 重投一批（256 条/ tick，失败则保留队首保序）；发件箱满才丢并告警。
（实现见 `world::BroadcastOutbox`；用进程级 `OnceLock` 是因为 `broadcast_to_map` 有 **101 处调用点**，
改签名要动 101 处且会与 `&mut self` 借用冲突——注释里写明"将来多世界分片必须改成 per-world 字段"。）

**实测把它证伪成"不是主因"**（信号分离后）：

| 并发 | 成功 | 单目标 `SendToClient` 丢弃 | 广播延迟投递 | 发件箱满 |
|---|---|---|---|---|
| 20 | 20/20 | **3377** | 0 | 0 |
| 30 | 25/30 | 483 | 0 | 0 |
| 50 | 31/50 | 9 | 0 | 0 |

即：广播路径的背压**根本没被触发**（deferred=0），剩下的丢包全部是
**单目标 `SendToClient`**（日志样例：`session=1 opcode=Some(56)/Some(65)/Some(12)`，正是进图对象包）。
单目标发送点全仓 **200+ 处**（player.rs 32、world/mod.rs 88、combat.rs 22、hero.rs 14、market.rs 13…），
挨个改不现实。

**结论：丢包不是"某个生产者缺背压"，而是"消费者被堵住"**——gate 处理 `StartGame` 时内联
`await world_ref.ask(...)`（建号 + 载图 + 发整段进场序列），期间整个 gate 邮箱只进不出，
谁在这一秒里想发东西谁就丢。所以**必须先做 ②**（把 StartGame 挪出 gate 串行路径），
消费端排队只是把队列从 gate 邮箱搬到世界侧，改变不了"消费者停摆"这件事。
（本条已按负结果记录：换来的经验是——先定位"消费者为什么停摆"，再谈给生产者加背压。）

### 3.6 ② 已落地（StartGame 移出 gate 串行路径）与结果

按上面那四步做的（PR #3036）：

1. **先让"置离线"竞态安全**：新增纯函数 `gate::actor::should_mark_account_offline(removed, remaining)`
   ——只有"该账号最后一个绑定会话"被清理时才置离线；`terminate_session` 改用它。
   门禁 `only_last_bound_session_marks_account_offline`（同账号两会话：旧会话断开不得置离线、
   最后一个断开必须置离线、未绑定会话啥也不做）；
   **阳性对照（实做）**：改成无条件 `Some(username)` → 门禁立即红
   （`left: Some("alice") / right: None`）→ 撤回复绿。
2. **再把 StartGame 挪出去**：gate 的 StartGame 分支不再内联 `await world_ref.ask(...)`，
   改为 `spawn("gate.startgame")` + 新消息 `StartGameFinished` 回投做顶号解绑。
   解绑顺序不再影响正确性（由第 1 条保证），因此可以安全地让 gate 立即返回继续收发。
3. 既有的顶号回归测试 `e2e_dup_kick_old_session_disconnect_keeps_account_online` 断言的是
   **旧机制**（"StartGame 应答时绑定已被内联摘除，不轮询"）→ 本轮把它改为断言**不变量**：
   绑定最终必须摘除（允许异步回投的短暂延迟，轮询 ≤1s），且**账号必须仍在线**（第三方同账号登录被拒）。
   机制变了、不变量没变。

**验收结果（单目标丢弃归零——这条就是本步骤的判据）**：

| 并发 | 成功（②前 → ②后） | 单目标丢弃（②前 → ②后） |
|---|---|---|
| 20 | 20/20 → **20/20** | 3377 → **0** |
| 30 | 25/30 → **30/30** | 483 → **0** |
| 50 | 31/50 → **50/50** | 9 → **0** |

**新的世界侧安全线**（继续往上压）：

| 并发 | 成功 | 单目标丢弃 | 登录 p95 |
|---|---|---|---|
| 80 | **80/80** | 0 | 0.035s |
| 120 | **120/120** | 0 | 0.013s |

即：这条线从本节开头的 **~10 会话**（20 会话就 1/20）抬到 **≥120 会话全绿零丢包**。
（120 之上未继续压：本机压测机与服务端同机，接下来该换独立压测机，见 §7。）

### 4.2 拆解（2026-09-23 本轮，工具 `tools/ops/memory_ramp.ps1`）

方法：对**同一份代码**的两种状态做 A/B（`git stash` 前后各 build 一次 release），同一台机器、
只加载 1 张图（`0.map`，700×700）、10/20 会话各保持 20s、全部进图成功（`ok=10/20`、`failed=0`）。
采样器每 2s 读一次 RSS 取保持期最大值（并修正了 `Process` 对象缓存属性必须 `Refresh()` 的坑）。

| 状态 | 10 会话 | 20 会话 | 每会话增量 |
|---|---|---|---|
| 修前（master f31ebf04） | 106.4 MB | 172.2 MB | 7.81 / 7.19 MB |
| 修后（`MapCache`/`Arc`） | 70.3 MB | **97.8 MB** | 4.13 / **3.50 MB** |
| 对照：只登录不进图 | — | 31.1 MB | 0.13 MB |

1. **大头 = 每个进图会话复制一整张地图**。`PlayerActor.map_data` 收到的是
   `SetMapData { map: MapData }` 的**全量克隆**（`cells: Vec<Vec<CellInfo>>`；
   `CellInfo` 8 字节 × 700×700 = **3.92MB**，外加 700 行 Vec 头与分配开销），
   而 4 处发送点（StartGame / 换图传送 / 绑定图回投 / GOTO）都是 `self.maps.get(..).cloned()`。
   地图加载后只读 → 改成 `MapCache(map_index → Arc<MapData>)`，玩家侧只留 `Arc`。
   实测 20 会话 RSS **172.2 → 97.8 MB（−43%）**、每会话 **7.19 → 3.50 MB（−51%）**。
   门禁：`map_cache_shares_one_arc_per_map`（`Arc::ptr_eq` + 强引用计数）+ 阳性对照实做
   （`get_arc` 改回每次克隆 → 立即红）。
2. **剩余约 3.5MB/会话仍在世界路径**：只登录不进图的对照只有 0.13 MB/会话，说明与 gate 会话本身无关；
   数值又恰好接近一张图（3.92MB），但代码里已无第二处 `MapData` 克隆。下一轮要查的是
   「入场时按会话留下的 ~3.5MB 挂在谁身上」（候选：入场大包/发送队列积压、按会话的实体快照）。
   ——**未定论，不许写成已解决。**
3. **登出后不归还（本轮新发现）**：20 会话全部登出后 RSS 只从 97.1 掉到 81.3 MB；
   紧接着再跑一轮 20 会话，保持期高水位 98.7 → 109.3、登出后 82.3 → 95.5 MB ——
   **每轮 20 会话净增 ~13MB（≈0.65MB/会话/轮）**。长时间运营里"连登连退"的人群会持续抬高常驻内存，
   需要单独定位（是残留引用还是分配器高水位只增不减）。

### 4.1b 「登出后不归还」定性更正（2026-09-24，release，高采样复核）

上面那条"每轮净增 ~13MB"的记法**会误导成线性泄漏**。用带**线程数/句柄数/admin 计数器**的
采样复核（`tools/ops/leak_plateau.ps1`，20 会话/轮）后，真相是**预热台阶 + 平台**：

| 轮次 | 20 会话登出后 idle RSS（release） |
|---|---|
| 预热 1 | 41.9 MB |
| 预热 2 | 42.9 MB |
| 预热 3 | 43.5 MB |
| 测量 1–5 | 43.0 / 43.2 / 43.3 / 43.9 / 43.4 MB → **斜率 0.1 MB/轮** |

同一批采样里，**线程数**在 idle 恒为 21（负载期 41–44）、**句柄数**恒为 136，
`online_players` 每轮回到 0、`tasks.running` 每轮回到基线 3（`spawned - finished` 恒为 3）。
只登录不进图的对照同样只看到预热台阶、之后斜率 ~0.1 MB/轮（早期 CAPACITY 记的
「连登连退每轮 +0.65MB/会话/轮」是 debug 构建 + 低采样密度下把预热段当成了趋势）。

结论（**取代**上面那条）：**没有每轮线性泄漏**；前 1~4 轮的抬升是 heap/懒初始化预热，
之后收敛到平台。判据固化成门禁 `tools/ops/leak_plateau.ps1`（J1 玩家记录回收 / J2 后台任务回收 /
J3 线程与句柄稳定 / J4 测量段 RSS 斜率 ≤ 0.5MB/轮），2026-09-24 实跑 `ok=true`。

### 4.3 复核（2026-09-23，master 5d1b079d）

同一 `memory_ramp.ps1`、同一 deploy 库、同一台机器：

| 版本 | 10 会话 | 20 会话 | 每会话 |
|---|---|---|---|
| #3042 之前 | 106.4 MB | 172.2 MB | 7.81 / 7.19 MB |
| #3042 之后（Arc 共享地图） | 70.3 MB | 97.8 MB | 4.13 / 3.50 MB |
| **本次复核（#3048 之后）** | **68.8 MB** | **96.5 MB** | **3.81 / 3.30 MB** |

**剩余 ~3.2MB/会话在「世界入场」这一段**：对照「只登录不进图」仍是 0.13 MB/会话（§4.2），
所以这 3.2MB 全部产生于进图路径，而不是会话本身。

**登出后不归还（复核仍成立）**：20 会话→全登出→等 25s，RSS 不回到 idle；紧接着再跑一轮 20 会话，
**cycle2 峰值 − cycle1 峰值 = +13.4MB（≈0.65MB/会话/轮）**，与 #3042 之前的观测一致
（当时 98.7→109.3）。也就是说：**大部分随峰值波动（高水位），但每轮确有 ~13MB 不再归还。**

**归因扫描（代码层，本轮做的）**：把 WorldActor 里所有「按 session 存集合/向量」的字段过了一遍
（`buyback_items` / `chat_items_sent` / `observe_links` / `npc_timers` / `npc_delayed_actions` /
`session_last_movement` / `tamed_pets` / `hero_paths` / `player_heroes` / 各类计数器）——**没有一个**
是 MB 量级；地图已改为 `Arc` 共享（§4.2）。因此当前主假设是：**入场序列那批「按会话构建/入队」的
大载荷（整图对象列表等）造成的分配器高水位**，外加每轮 ~13MB 的真残留；而不是某个显式的每会话大结构。

**下一步（明确、可判定）**：① 在入场序列打一次「本会话入队字节数」的 debug 日志，量出每会话真实载荷；
② 把入场大包改成**世界级复用缓冲**或分块发送，然后重跑本节的两条测量（10/20 会话 + 双轮 cycle），
判据 = 每会话增量下降且 cycle2−cycle1 明显缩小。

外推（本改动后、单图、单机）：`RSS ≈ 28MB + 3.5MB × 会话数` → 200 会话约 **0.73GB**（修前外推约 1.5GB）。

### 4.4 入场载荷定量（2026-09-24，验收 `MIR2_EGRESS_STATS=1`）

§4.3 的下一步①已落地：`ServerRust/src/util/egress_stats.rs` 按 opcode 记「包个数 × 尺寸」，
`GateActor` 在**会话收尾**时打一行 `EGRESS_STATS session=<id> packets=.. bytes=.. top=<op>:<count>/<bytes>/<max>,..`
（默认关闭，仅 `MIR2_EGRESS_STATS=1` 生效——热路径只多一次 bool 判断）。
测量：`memory_ramp.ps1` 10 会话（同一 deploy 库、同机、debug 构建），逐会话读数如下：

| 会话 | 帧数 | 字节 | 最大单包 |
|---|---|---|---|
| 10（最晚入场） | 3009 | 235.1 KB | 23.5 KB |
| 2 / 4 / 7 / 8 / 9 | 2467–2942 | 198.9–230.3 KB | 23.5 KB |
| 1 / 3 / 5 / 6 | 2299–2805 | 188.2–224.3 KB | 23.5 KB |

同一份读数里，**每会话的载荷构成几乎完全一致**（取 top）：

| opcode | 含义 | 包数 | 字节 | 最大 |
|---|---|---|---|---|
| 71 | `ObjectMonster` | **1912** | **106.6 KB** | 70 |
| 30 | `Chat` | 75–775（随在线时长增长） | 6.4–66.4 KB | 91 |
| 204 | `NewQuestInfo` | 157 | 27.9 KB | 544 |
| 266 | `NewRecipeInfo` | 1 | 23.5 KB | 23470 |
| 250 | `GameShopInfo` | 1 | 3.5 KB | 3511 |
| 18 | `NewMapInfo` | 1 | 1.5–14.7 KB | 14703 |
| 92 | `ObjectNpc` | 43 | 2.1 KB | 57 |

**结论（把 §4.3 的「分配器高水位」假设落到了具体机制）**：入场出站 188–235 KB/会话里，
**`ObjectMonster` 占帧数的 71%、字节的 45–57%**——服务端日志同一轮写着
`Spawned 43 NPCs and 1912 monsters for session N`，即**每个会话入场都会按会话重新生成一份整图 NPC/怪物
（`spawn_npcs_and_monsters(.., session_id, ..)`，object_id 逐会话递增）并插入世界表**。
20 个会话同图在线时，同一张图的怪物条目就有 **1912 × 20 ≈ 38k 份**同时驻留；
而清理只在「该地图已无其他玩家」时执行（`cleanup_map_spawns`，见 `PlayerDisconnected` / `PlayerLogOut`），
所以一轮 20 会话期间这条曲线是**单调累积**的。以 `MonsterState`（含 `String name` + AI 状态）量级估算
38k × ~350B ≈ **13MB**，与 §4.3 实测「cycle2 − cycle1 = +13.4MB（0.65MB/会话/轮）」吻合。

**下一步（判据已明确）**：把「按会话生成整图怪物/NPC」收敛成**按地图单一真源**（或以会话为属主的
增量挂载 + 断开时只摘自己那一份并释放容量），然后重跑本节两条测量：
① 10/20 会话的每会话增量下降；② 双轮 cycle 的 `cycle2 − cycle1` → 接近 0。
在拿到这两条之前，残余内存**不计入已解决**。

**同轮修掉的标定夹具坑（`tools/ops/memory_ramp.ps1`）**：
① 部署副本的 gate 端口现在会按 `-Port` 自动对齐——此前不对齐会让实例去抢 7000，
   绑定失败的唯一表现是日志里没有 `Gate listening`，脚本却照记 `ready=false`（静默作废的标定）；
② 就绪失败改为**硬失败（exit 2）**而不是产出一行 `ready=false`；
③ `out/` 目录先建（`-RedirectStandardOutput` 指向不存在的目录会直接启动失败）；
④ 服务端 admin 端口从「固定 7001」改为**跟随 gate 端口 +1**（`util::admin::admin_port_for`），
   否则同机第二个实例的观测面会静默失效（日志只剩一行 ERROR）。

### 4.5 地图级生成物单真源（2026-09-24，修掉 §4.4 定位的机制）

**改动**（`ServerRust/src/actors/world/{mod,session,map_sync}.rs`）：该图生成物**已物化**时，
后续进场会话只按**既有 object_id** 重放（`send_map_spawns_to_session`），不再各自生成一份；
`map_spawns_ready` 标记对空配置不置位，`cleanup_map_spawns` 释放地图时清标记。
对齐原版 C# `Map.Objects` / `GetObjectsPassive`，同时修掉「两个玩家各自看到自己的怪、打不到同一只」。
门禁 `e2e_same_map_second_session_reuses_spawns`；阳性对照实做（复用判断强制 false → 计数 3→6 立即红）。

**测量**（同一 deploy 库、同一台机器、同一天背靠背；A/B 用同一份代码的两种状态各 build 一次
`mir2_server`，10/20 会话各保持 20s，各档 `ok` 全数、`failed=0`）：

| 状态 | 10 会话 | 20 会话（两轮） | 20 会话档 per-session | 10→20 边际 |
|---|---|---|---|---|
| master（修前，同构建） | 117.7 MB | **152.2 / 146.8 MB** | 4.50 MB | **+34.5 MB** |
| 本改动（修后） | 117.4 / 121.0 MB | **122.5 / 121.7 MB** | 3.22 MB | **+5.1 MB** |

**机制铁证（服务端日志逐行计数，同一天 20 会话档）**：

| 二进制 | `Spawned … monsters` 行 | 生成怪物条目 | `spawns reused` 行 |
|---|---|---|---|
| master | 20 | **38,240**（1912 × 20） | 0 |
| 本改动 | **1** | **1,912** | **19** |

即：20 会话同图，修前世界里同时驻留 20 份整图怪物，修后只有 1 份、其余 19 个会话是重放。
20 会话档 RSS **152.2 → 122.5 MB（−19.5%）**、`rss_per_session` **4.50 → 3.22 MB（−28%）**、
10→20 会话的**边际**成本 **+34.5 → +5.1 MB**。这也把 §4.3/§4.4 里
「剩余 ~3.2MB/会话在世界入场段且归因不明」的那部分收口到了具体机制上。

**如实记两条未达成的**：

1. **10 会话档两者几乎相同**（117.7 vs 117.4）：该档被一个与本改动无关的固定分量主导
   （idle 57–62 MB → 载荷 117 MB，10 个会话就要 +55 MB）。单独第三次跑 10 会话（warm）仍是 121.0 MB，
   说明不是「首轮冷启动」效应。所以**10 会话档不能用作本改动的判据**，判据取 20 会话档与边际值。
2. **§4.3 的「登出后不归还 +13.4MB/轮」本轮未复现**：同二进制连跑两轮 20 会话，
   master 峰值 −5.4 MB、本改动 −0.8 MB（两条都是负增长）。因此本次只用「20 会话档 + 机制计数」
   证改动有效；`cycle2 − cycle1` 今日在两种代码上都接近 0，**不构成差异证据，也不据此宣称已解决**。

**下一步**：把 `Spawned`/`reused` 计数做成可断言的门禁（当前只在实机日志里），
并在 **release 构建**下复测同一组 10/20 会话 + 双轮 cycle（本次两侧都是 debug，绝对值不可与 §4.2/§4.3 的 release 数值直接比）。

### 4.1 release 构建复核 + 「登出后不归还」定性（2026-09-24）

上面 §4 的绝对值来自 **debug 构建**，不能与线上直接比。同一台机、同一夹具
（`tools/ops/capacity_ramp.ps1`，各档保持 20s），把服务端换成 **release 构建**复测：

| 档位 | idle RSS | 载入后 RSS | 每会话 | 登录 p95 | 丢包 / 踢线 |
|---|---|---|---|---|---|
| 10 会话 | 30.3 MB | 48.3 MB | 1.80 MB | 0.006 s | 0 / 0 |
| 20 会话 | 31.2 MB | **50.8 MB** | **0.98 MB** | 0.006 s | 0 / 0 |

10→20 会话**边际**仅 **+2.5 MB**（+0.25 MB/会话）。对比修复前的 release 基线（§4 表：20 会话
176.3 MB / 7.4 MB/会话）——每会话 **−87%**，机制是「地图级生成物单真源」（#3062：整图 NPC/怪物
不再按会话各复制一份）。

**「登出后不归还」复现并量化**（release，20 会话 × 5 轮；每轮 = 登录 20 → 保持 20s → **全部断开** → 静置 45s）：

| 轮次 | 载入后 | 全断开 + 45 s 后 |
|---|---|---|
| idle（无会话） | — | 31.6 MB |
| 1 | 46.3 MB | 46.7 MB |
| 2 | 48.3 MB | 48.6 MB |
| 3 | 49.4 MB | 49.4 MB |
| 4 | 50.5 MB | 50.5 MB |
| 5 | 51.0 MB | 51.2 MB |

结论：**确实不回落**（相对 idle 保留约 **+15 MB**），但**不是每轮线性泄漏**——第 1 轮一次性 +15.1 MB
之后，其后每轮只 +0.6~1.1 MB，5 轮后趋平在 ~51 MB。据此定性为「**分配器保留区为主 + 少量会话级残留**」
（依据：首轮一次性增量 + 跨轮次趋平），不是无界泄漏；生产上若要收紧属于分配器/工作集调优项
（如 `malloc_trim` / `SetProcessWorkingSetSize`），不是缺陷。

## 6. 结论与下一步（按优先级）

**当前单机安全线**（② 之后）：**世界会话 ≥120 全绿、零丢包**（120/120，见 §3.6）；
登录并发 100 真延迟 p95 0.35s、200 并发 p95 0.86s（见 §2.1）。
本节开头的「~10 会话」是最初基线，中间经过 gate 接入并行化、扇出批量、argon2 出 actor、
map_index 单一漏斗缓存、广播有界发件箱、StartGame 移出 gate 六步。

1. **给世界→客户端的扇出加"可丢弃"语义**：非关键广播（视野内实体更新等）应按 tick 合并/丢旧，
   而不是把 gate 邮箱打满后丢新包。
2. **按 tick 合并实体更新**：现在每个事件独立 `SendToClient`，20 人同图即 20 倍扇出。
3. ~~拆解 7.5MB/会话~~ **已做（§4.2 + §4.5）**：① 每会话一张整图克隆 → `Arc` 共享（−51%/会话）；
   ② 每会话一份整图 NPC/怪物 → 地图级单真源（20 会话 152.2→122.5 MB，10→20 边际 +34.5→+5.1 MB）。
   **仍待做**：release 构建下复测（§4.5 两侧都是 debug）、「登出后不归还」本轮未复现需另查。
4. **高负载 tick 滞后**：拉长窗口（≥2 分钟）在 10/20/50 会话各测一次心跳滞后。
5. **独立压测机 + 生产拓扑**：本机测不出网络 RTT、带宽与真实客户端渲染开销。
