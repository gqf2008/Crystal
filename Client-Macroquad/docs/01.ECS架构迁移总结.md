## 2. 架构设计

### 2.1 ECS 核心三要素

#### **实体 (Entity)**
- 使用 `hecs::Entity` (唯一标识符)
- 通过组件组合定义行为

#### **组件 (Component)**
- 纯数据结构，无逻辑
- 按职责分类：
  - `core/` - 核心组件 (Position, Health, etc.)
  - `movement/` - 移动相关
  - `combat/` - 战斗相关
  - `network/` - 网络同步
  - `rendering/` - 渲染状态
  - `input.rs`, `map.rs` 等单文件组件

#### **系统 (System)**
- 实现游戏逻辑
- 分为 LogicSystem 和 RenderSystem
- 按层级优先级执行

### 2.2 System Trait 设计 (Macroquad 风格)

```rust
// src/systems/mod.rs

/// 逻辑系统 - 处理游戏逻辑更新
pub trait LogicSystem {
    fn update(&mut self, ctx: &mut GameContext, delay_time: f32) -> GameResult;
}

/// 渲染系统 - 处理画面绘制
pub trait RenderSystem {
    /// 可选的逻辑更新 (例如动画帧更新)
    fn update(&mut self, _ctx: &mut GameContext, _delay_time: f32) -> GameResult {
        Ok(())
    }
    
    /// 绘制函数 - 使用 macroquad 全局函数
    fn draw(&mut self, world: &GameWorld) -> GameResult;
}
```

**设计原则**:
1. **简化参数**: 移除 ggez 的 `GraphicsContext` 和 `Canvas`
2. **全局渲染**: 使用 macroquad 的全局函数 (`draw_texture`, `draw_text`, etc.)
3. **职责单一**: LogicSystem 只处理逻辑，RenderSystem 只处理渲染

## 6. 关键技术决策

### 6.1 为什么选择 macroquad？

1. **跨平台** - 支持 Windows/macOS/Linux/Web/Android/iOS
2. **简单易用** - 全局函数式 API，无复杂上下文
3. **性能优秀** - 基于 miniquad，轻量级渲染
4. **活跃维护** - 社区活跃，更新频繁

### 6.2 为什么保留 hecs？

1. **性能优秀** - 基于原型的 ECS，内存访问高效
2. **API 简洁** - 查询语法直观
3. **已验证** - ClientRust 中已充分验证

### 6.3 为什么使用 crossbeam_channel？

1. **高性能** - 比 std::mpsc 更快
2. **无界通道** - 支持 unbounded channel (网络模块需要)
3. **丰富功能** - 支持 select, timeout 等

## 8. 注意事项

### 8.1 ECS 设计原则

1. **组件纯数据** - 不包含逻辑，只有数据字段
2. **系统单一职责** - 每个系统只处理一个明确的功能
3. **查询高效** - 使用组合查询，避免单个组件大量迭代

### 8.2 命名规范

- **组件**: 名词，描述状态 (Position, Health, Velocity)
- **系统**: 动词+System (MovementSystem, CombatSystem)
- **文件**: snake_case (movement_system.rs, combat_stats.rs)

### 8.3 文档规范

- 每次重大设计/重构必须创建文档
- 文档编号: `YYYYMMDD.NN.标题.md`
- 统一放置在 `docs/` 目录
